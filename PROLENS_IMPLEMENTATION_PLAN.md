# ProLens Implementation Plan

ProLens is an independently branded Kubernetes IDE maintained as a fork of
[Freelens](https://github.com/freelensapp/freelens) (itself a fork of OpenLens).
This document records the architecture of the codebase as ProLens inherits it,
the work that turns it into ProLens, and the risks of that work.

## 1. Repository architecture

| Area                 | Location                                                                                         | Notes                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Package management   | `pnpm-workspace.yaml`, root `package.json`                                                       | pnpm (pinned via `packageManager`), exact versions through the pnpm catalog, Node >= 24                                            |
| Task runner          | `turbo.json`                                                                                     | `pnpm build` builds packages then the app                                                                                          |
| Electron shell       | `freelens/`                                                                                      | electron-vite build (`electron.vite.config.ts`), electron-builder packaging (`electron-builder.yml`), installer assets in `build/` |
| Main process         | `freelens/src/main/index.ts` → `packages/core/src/main`                                          | Bootstrap, windows, tray, menus, proxies, kubectl/helm, shell sessions                                                             |
| Renderer process     | `freelens/src/renderer/index.ts` → `packages/core/src/renderer`                                  | React 19 + MobX 7 UI, root frame and per-cluster frames                                                                            |
| Shared code          | `packages/core/src/common`, `features/*/common`                                                  | Must only use APIs present in both environments (`pnpm type:check:environments`)                                                   |
| Dependency injection | `@ogre-tools/injectable`                                                                         | Every feature is a set of injectables; `register-injectables.ts` files are generated by `pnpm build:di`                            |
| Application identity | `freelens/package.json` (`productName`, `config`) → `applicationInformationToken`                | `productNameInjectable`, `appNameInjectable` derive window titles and the user-data path                                           |
| Themes               | `packages/core/src/renderer/themes`                                                              | `LensTheme` declarations (injection token), applied as CSS custom properties on `<html>`                                           |
| Preferences          | `packages/core/src/features/user-preferences`                                                    | Descriptor per preference (`fromStore`/`toStore`), MobX state, persisted with `conf` in `lens-user-store.json`                     |
| Preferences UI       | `packages/core/src/features/preferences/renderer/preference-items`                               | Tabs, pages and blocks registered through `preferenceItemInjectionToken`                                                           |
| Terminal             | `packages/core/src/renderer/components/dock/terminal`, `main/shell-session`                      | xterm.js in the dock, node-pty in main; `sendCommandInjectable` opens a tab and types into it                                      |
| Kubernetes client    | `packages/kube-object`, `packages/core/src/common/k8s-api`                                       | Requests go through the local Freelens proxy and the bundled `freelens-k8s-proxy`                                                  |
| Extension API        | `packages/extensions`, `packages/core/src/extensions`                                            | Published as `@freelensapp/extensions`; extensions find it on `globalThis.FreelensExtensionApi`                                    |
| Top bar              | `renderer/components/layout/top-bar`                                                             | Items registered via `topBarItemOnLeftSideInjectionToken` / `topBarItemOnRightSideInjectionToken`                                  |
| Tests                | Vitest (`vitest.config.ts`), integration tests in `freelens/integration` (Playwright + Electron) | `pnpm test:unit`, `pnpm test:integration`                                                                                          |
| CI/CD                | `.github/workflows`                                                                              | Type check, unit tests, integration tests, release (`release.yaml`), apt repository, npm publish                                   |

## 2. Compatibility boundaries (not renamed)

These identifiers are consumed by third-party extensions, the Kubernetes
ecosystem or the upstream merge path, and stay as they are:

- `@freelensapp/*` package names, the `freelens` workspace directory and package name (Turbo filters, upstream merges).
- `globalThis.FreelensExtensionApi`, the `freelens` field in an extension's `engines`, and every extension API type name.
- Internal identifiers such as `FreelensProxy`, `freelens-k8s-proxy` (a separately released binary), and env vars like `FREELENS_PROXY_TOKEN`.
- Copyright headers (`Freelens Authors`, `OpenLens Authors`) and `LICENSE`: ProLens keeps the upstream MIT attribution.
- `freelens://` deep links are still **accepted** when passed to ProLens, but ProLens registers itself only for `prolens://`, so both apps can be installed side by side.

## 3. Work items

### Phase 2 — Branding

1. Central branding module `packages/core/src/common/branding.ts` (product name, app ids, protocol scheme, URLs, certificate authority names, user agent) and a unit test that checks `freelens/package.json` and `freelens/electron-builder.yml` agree with it.
2. New application identity: `appId: app.prolens.ProLens`, product name `ProLens`, user-data directory `ProLens` (`ProLensDev` in development) — isolated from Freelens.
3. Protocol `prolens://` (legacy `freelens://` still parsed).
4. User-facing strings (dialogs, error popups, preferences, splash screen, User-Agent, CA names).
5. Icons: new ProLens SVG logo; regenerate `.icns`/`.ico`/PNG sets and tray icons from it.
6. Linux metadata (desktop/metainfo/apparmor), Windows NSIS, macOS bundle id; drop the Freelens apt repository keys from the `.deb`.
7. README, release workflow artifact names.

### Phase 3 — Theme engine

1. Extend `LensTheme` with ProLens built-ins: ProLens Dark (default), ProLens Light, Midnight, Graphite, Nord, Aurora, High Contrast. "System" is the existing `colorTheme = "system"` preference, which now follows the OS between ProLens Dark and ProLens Light.
2. Theme customisation preferences: accent colour, density (compact/comfortable), font size, custom themes (JSON), applied via CSS custom properties and `data-*` attributes on `<html>` from the existing apply step.
3. Custom themes: JSON schema (`name`, `type`, optional `extends`, partial `colors`/`terminalColors`), validated with `zod`; import/export through file dialogs; custom themes appear in the theme and terminal-theme pickers.
4. Theme gallery in Preferences → Appearance with live preview swatches and one-click switching.

### Phase 4 — AI tools

1. Provider registry: `aiProviderInjectionToken` in `features/ai-tools/common`; one injectable per provider (Claude Code, Codex CLI, GitHub Copilot CLI, Gemini CLI, OpenCode, Custom).
2. Per-provider settings (executable path, arguments template with a `{prompt}` placeholder), default provider preference.
3. Detection in main: resolve the executable on the shell `PATH`, report `installed` / `not-installed` / `error`, with version where available.
4. Preferences → External Tools → AI Tools page (status, refresh, path/argument editors, install instructions per platform).
5. Top-bar AI selector: switch the active assistant and launch Ask AI without restarting.

### Phase 5 — Ask AI

1. `AskAiDialog`: preset questions, free-text prompt, opt-in checkboxes for events and logs, preview of the exact context that will be sent.
2. Context builder: cluster, namespace, resource kind/name, sanitised YAML (Secrets redacted, managed fields dropped), and — only when ticked — events and recent logs.
3. Entry points: top bar, cluster overview, every kube object context menu (pods, deployments, nodes, …), events page, logs dock tab, resource YAML editor tab.
4. Safety: read-only defaults per provider where the CLI supports them (Claude Code `--permission-mode plan`, Codex `--sandbox read-only`); the prompt instructs the assistant not to change the cluster without explicit approval; the command is run in a cluster terminal, never executed silently.

### Phase 6 — Extensibility

1. `aiContextSourceInjectionToken`: pluggable context providers (events, logs today; Prometheus, Argo CD, Helm later).
2. `AiBackend` interface for API-based backends (Ollama, OpenAI-compatible endpoints, MCP servers), documented in `docs/prolens/ai-extensibility.md`.
3. Prompt redaction utility for tokens, passwords and certificates.

### Phase 7–8 — Quality

Unit tests for branding consistency, theme switching and customisation, custom theme validation, provider registry and argument building, detection, prompt context building. Type check, unit tests and build run locally on macOS.

## 4. Risks

| Risk                                                                              | Mitigation                                                                                           |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Upstream merges conflict with renamed files                                       | Rename strings, not files or identifiers; new code lives in new files under `features/`              |
| Extensions break because of identity changes                                      | Extension API, globals and `engines.freelens` untouched                                              |
| Users lose settings when the user-data directory changes                          | ProLens is a separate app by design; it starts with fresh settings and does not touch Freelens' data |
| AI CLI flags change between releases                                              | Argument templates are user-editable per provider                                                    |
| Prompts leak secrets                                                              | Secret data redacted, managed fields stripped, logs/events opt-in, redaction pass on all context     |
| Long prompts exceed terminal/OS argument limits                                   | Context is truncated per section with a visible marker                                               |
| Code signing, notarisation and Windows/Linux packaging cannot be verified locally | Reported as untested; release workflow keeps the same structure                                      |

### Done in the second pass

- Welcome screen uses a ProLens logo component; the stale Freelens `packages/core/build/icon.png` is replaced. The `logo-lens` icon name stays in the extension API.
- The update check (welcome notification and About dialog) reads the latest GitHub release of `branding.releasesRepository`; the npm lookup stays for extension installs.
- Release workflows run only in `chago1991/prolens` (release, npm-version, tag) and publish to its own releases. Apple notarization and Azure signing are optional: without the secrets the release is built unsigned and stapling is skipped. Publishing to npm and the release scan stay upstream-only. `notarize.cjs` defaults to `app.prolens.ProLens`.
- The Freelens APT repository workflow and keys are removed; the README lists only ProLens' own releases.
- **AI session gate**: each launch gets its own proxy token. Reads pass; mutations, Secret reads and exec/attach/port-forward/proxy are held for the user's approval of that one request in the main window, and denied after two minutes. See `docs/prolens/ai-extensibility.md`.
- Fixes found in UI testing: the cluster overview button no longer takes a cell of the overview grid; an answered or expired approval prompt is withdrawn by main; theme gallery in design order; the top bar preselects "Assess cluster health"; fixed SVG ids for stable snapshots.

### Verified

- `pnpm type:check`, `pnpm biome check` on every changed file, `pnpm knip:check`, actionlint on the edited workflows (no findings beyond those of the unmodified files).
- `pnpm test:unit`: every test file passes. Snapshots were regenerated only for the files the welcome logo and the gallery order changed, after reviewing their diffs.
- `pnpm test:integration` against a local kind cluster: all files pass (the skipped tests are skipped upstream). One run failed once on a fresh cluster (image pull and pod termination over the test's fixed 30 s waits) and passed on the rerun and the final full run.
- Packaged macOS app driven with Playwright: theme selection, accent, density, font size, live AI tool switching, persistence across restart; Ask AI from the top bar (root → cluster frame), the overview and the pod menu.
- Claude Code launched from the pod menu, ran kubectl against the cluster through ProLens, and its delete was held and denied by ProLens even after its own plan-mode prompt was answered "yes"; the pod survived.
- An agent stand-in (custom command) proved: reads pass; denied delete, Secret read and exec fail with ProLens' message; approved ones run once; an unanswered request is denied and withdrawn at two minutes.
- Icons: every generated asset shows the ProLens mark. Coexistence: Freelens and ProLens ran side by side; `freelens://` opens Freelens and `prolens://` ProLens; ProLens wrote only to its own directories.

### Not verified / remaining

- Codex CLI starts in the ProLens terminal with its prompt, but the account it is signed in with rejects every model tried, so it did not run kubectl. Its read-only sandbox blocks network access, so Codex needs its own approval for each kubectl it runs.
- Gemini CLI and OpenCode are not installed here.
- Windows and Linux builds, signing, notarization and the release workflows themselves were not run.
- The gate does not stop an assistant from using credentials it can read from disk (such as the original kubeconfig); see "Limits" in `docs/prolens/ai-extensibility.md`.
