## Goal

Port this extension from the Freelens v1 extension API to the **v2 extension API**, so that it loads and works on Freelens 2.x, and align its build stack with the current Freelens stack.

The work is done mostly by the Claude agent in CI (`.github/workflows/claude.yaml`), one or more steps per @<!-- -->claude comment from a maintainer, with maintainers reviewing each step and answering with another @<!-- -->claude comment when it needs corrections. This issue is the plan; the PR is the working record.

Sections marked **(project-specific)** are written for this repository: the inventory, the functional checks and the decisions. freelensapp/freelens-example-extension#326 is the same plan carried out for the template itself, with its results and findings.

## Plan (generic)

Each step is one commit on the PR branch. A step that changes how the project is built, laid out, tested or written updates `AGENTS.md` in the same commit, so the guide never lags the code. `AGENTS.md` describes the current practice only: no dates, no account of how things were done before v2 or why they changed, no migration notes. After each step the agent pushes it and reports in the PR (what changed, validation output, open questions); how many steps one run does is in "Rules for the CI agent". Steps 1-4 leave the tree buildable only together, so validation is partial until step 4; say which checks are expected to fail and why.

- [ ] **0. Surface check (no code changes).** Install the `@freelensapp/extensions` version named in "Source of truth" in a scratch location and confirm that every API symbol listed in the inventory exists in the v2 `extension-api.d.ts` with a compatible signature; look each one up in the "v1→v2 rename table" of the migration guide. For every class the extension extends (stores, KubeObjects), check whether the v2 base class uses `accessor` fields and how it serializes, since that decides how step 4 migrates decorators. Post the result as a PR comment.
- [ ] **1. Manifest, dependencies and toolchain.** `engines.freelens: ^2.0.0`; `"type": "module"`; `version` bumped to a prerelease of the next major (`pnpm version premajor --no-git-tag-version`: 0.2.2 becomes 1.0.0-0, 1.4.2 becomes 2.0.0-0), unless "Decisions" says otherwise; `@freelensapp/extensions` as a semver range from the version of "Source of truth" (`^2.0.0`), where the template's own `package.json` pins one exact version; every other version per "Stack alignment", host-provided libraries as devDependencies only; a bundled library that the catalog moves to a new major is source work: step 1 changes its version only, the code the major breaks is adapted in step 4 or in the feature issue that uses it, and the step 1 report names every such major; add `electron` (types only) and `esbuild`; remove whatever only the v1 setup needed. Node, `mise.toml`/`mise.lock` and script tool versions as in Freelens. `/tmp/` in `.gitignore`, with the template's comment ("Scratch space of the CI agent, which checks out Freelens at tmp/freelens."), so that `pnpm biome:check` passes from this step on. Update `pnpm-lock.yaml`.
- [ ] **2. Build.** `vite.config.mjs` based on the fixture extension's. Requirements: host-provided modules resolve to `globalThis.FreelensExtensionApi` per the C3 table and its per-process column; the renderer bundle has no Node builtins marked external and no bare imports left; main keeps builtins external; main is built for Rolldown's `node` platform (`build.rolldownOptions.platform`), so that a bundled CommonJS package can `require()` the builtins, and defines `__dirname` and `__filename` as `import.meta.dirname` and `import.meta.filename`, which Rolldown leaves as they are in a bundled CommonJS package; standard decorators are lowered; exactly one CSS asset is emitted next to the renderer entry; the CSS module declarations are written by the plugin of "Stack alignment"; `main`/`renderer` in `package.json` point at the new outputs. If the v1 setup had a workaround for a real bundler failure, keep its effect if it still applies, otherwise remove it and say why.
- [ ] **3. TypeScript layout.** `tsconfig.base.json` with the Freelens compiler options, plus `src/main`, `src/renderer`, `src/common` configs as in "Source layout: one tsconfig per runtime environment" of the migration guide; a root config only for tooling files (Vite and Vitest configs); `type:check` runs all of them. The environment tests per "Stack alignment", with `@ts-expect-error` lines proving the split (Node API rejected in renderer and common, DOM rejected in main and common). Tests get their own program per "Test context".
- [ ] **4. Source migration.** Every inventory item in `src/`, and anything step 0 or the type check surfaces. Code covered by a feature issue gets only the smallest change the type check and build need, in this commit; its adaptation proper is done in the feature issue's steps. The model of every custom resource the extension presents with a sidebar entry and pages of its own is listed in `customResources` of the renderer extension, so the Custom Resources tree of the cluster sidebar does not list it a second time; a model the extension only decorates with details or menu items stays out of it (C6, and the checklist of the migration guide).

- [ ] **6. Tooling, metafiles and CI.** Biome, knip, Renovate and the other metafiles synced per "Stack alignment"; `pack:dev`, `clean*` scripts and `.gitignore` for the new output paths; `pnpm knip:check` and `pnpm trunk:check` clean. - [ ] no unlowered decorator (`@observable`, `accessor`) in the output
- [ ] one CSS file next to the renderer entry

### Validation by maintainers (generic, local, Freelens v2)

These checks and the functional checks below run in Freelens dev, by hand or by an agent attached over CDP, as "Checking the Extension in Freelens Dev" in the [`AGENTS.md`](https://github.com/freelensapp/freelens-example-extension/blob/main/AGENTS.md#checking-the-extension-in-freelens-dev) of freelensapp/freelens-example-extension describes.

- [ ] extension accepted at discovery (`isCompatible: true`) and loads without console errors in both processes
- [ ] directory install: rebuilding reloads the extension without restarting Freelens (ESM main)
- [ ] state changes made through mobx are reflected in the UI (host mobx instance, not a copy)

## Rules for the CI agent (generic)

- Each run is started by a maintainer's @<!-- -->claude comment: on this issue until the PR exists, on the PR afterwards. Do what that comment asks and nothing beyond it.
- The first run creates the branch `claude/issue-<this issue number>-migrate-freelens-api-v2` and opens one PR as a draft (`gh pr create --draft`). GitHub needs a commit to open a PR and step 0 changes no code, so that run starts the branch with an empty commit (`git commit --allow-empty`); a squash merge leaves no trace of it on `main`; how the PR is merged and whether the port lands in one PR or in stages is in "Decisions". The PR has `Closes #<this issue>` and `Closes #<feature issue>` for every feature issue in its description; the PR description mirrors the checklists of this issue and, in a separate section per feature issue headed as project-specific, the checklist of that issue, all kept in sync.
- Steps of this issue are numbered (`0`-`7`), steps of a feature issue carry a prefix of its own, which the feature issue names (for example `E0`, `E1`, ...). Name the step in every commit body and report comment, so it is always clear which issue a change belongs to. A finding about the v2 API or the migration in general goes here; a finding about one feature goes to its issue.
- Do not change anything under `.github/`. When a step needs a workflow change, write the complete new or changed workflow files under `github-workflow-fix/` in the repository root, with the same file names as in `.github/workflows/`, commit them with the step, list them in the report and note them in the PR description as proposed workflow changes, as "Modifying GitHub Actions Workflows" in the Freelens `AGENTS.md` describes. Maintainers move them into `.github/workflows/` in a separate commit and remove `github-workflow-fix/`. Pull before continuing, as the branch may have gained such commits.
- One commit per step; plain commit subjects, no Conventional Commits prefix; no emoji. A correction requested in a review comment is a new commit, not a rewrite of the step's commit.
- A run does the steps its comment asks for, one or more, in order. After each step, before the next one starts: run its validation, commit, push to the PR branch, update the checklists in the PR description and post the step's report. A run cut off by the job timeout or the turn limit then loses at most the step in progress.
- Stop early, after pushing and reporting the step, when it needs a workflow change under `github-workflow-fix/` that the next steps depend on, when a validation fails for a reason outside the step, or when a `Finding:` changes the plan. Say why the run stopped and which step comes next.
- What usually ends a long run is the turn limit of the agent's job in `claude.yaml` (its `--max-turns`), not its `timeout-minutes`. A trigger comment asks for a set of steps that fits in both; check them before the first run, and raise them or size the trigger comments to them. Before the turns or the time run short, stop at a step boundary and say which step comes next.
- The system prompt of the CI agent is `AGENTS.md` from `main`, which describes the v1 setup until this PR is merged. Where it disagrees with this issue on anything the migration changes (build, dependencies, host globals, layout), this issue wins; the PR branch's own `AGENTS.md` is the one being updated.
- The workflow checks out freelensapp/freelens `main` at `tmp/freelens`. The references in "Source of truth" are pinned to a release tag; the checkout is shallow, so fetch that tag first (`git -C tmp/freelens fetch --depth 1 origin tag <tag>`) and read them there (`git -C tmp/freelens show <tag>:<path>`), and report as a finding anything relevant that `main` has changed since. `.gitignore` ignores `/tmp/` from step 1 on; without it, Biome finds the checkout's own root `biome.jsonc` and `pnpm biome:check` fails.
- When the work needs something the specification or this plan does not cover, or contradicts it, report it in the PR as a separate comment headed `Finding:`, with the evidence (error output, the `.d.ts` excerpt, the doc section) and the change to this issue you propose. Do not edit this issue yourself; maintainers fold findings in. If the finding needs a change in freelensapp/freelens, say so and propose the entry for "Upstream work item"; do not open issues or pull requests there.
- Do not work around a missing API symbol with `as any`, `globalThis.require` or reaching into host internals. Report it instead; per the migration guide a missing re-export is an upstream bug.
- Follow the repository's `AGENTS.md`.
